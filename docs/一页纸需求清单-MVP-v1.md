# 共享设备借用 · 一页纸需求清单（MVP v1）

> 基线：2026-10-30 需求评审，Q1–Q10 全部选择 A 档（最简档）。用户：企业员工 + 管理员。
> 定位：**把"谁在什么时段占了哪台设备"变成一条数据库唯一约束 + 一条可查记录。** 不做流程、不做硬件、不做集成。
> 技术结论：单体应用 + 4 张表 + 1 条唯一索引 + 2 态状态机。参考工作量 15–20 人日（不含 UI 美化与培训）。

## 一、范围边界

**做**：设备台账 · 时段预约 · 硬冲突拦截 · 取还登记 · 操作留痕 · 管理员处置。
**不做**：审批流 · 维护工单 · 扫码/智能柜 · SSO · 外部集成 · 费用与信用 · 统计看板。

## 二、角色与权限（只有 2 个角色）

| 角色 | 可以 | 不可以 |
|---|---|---|
| 员工 | 查设备、看占用、预约/取消自己的、登记取走与归还、看自己历史 | 改设备、改他人预约、改历史记录 |
| 管理员 | 设备增删改、设备上下架、强制取消任意预约、看全员预约与超期清单、导入/停用账号 | 删除已产生的操作日志 |

设备状态**只能由管理员变更**；员工对设备的任何写操作都不允许。

## 三、数据模型（4 张表，不许多）

- `users`：id、emp_no（唯一）、name、dept、role、status、pwd_hash
- `devices`：id、asset_no（唯一）、name、model、location、status、note
- `bookings`：id、device_id、slot_date、slot_start、slot_end、user_id、status、picked_at、returned_at、remark、active_flag
- `op_logs`：id、actor_id、action、target_type、target_id、before、after、at、ip

**核心约束（整个 MVP 的技术核心）**
- `UNIQUE(device_id, slot_date, slot_start, active_flag)`；`active_flag` 有效时 = 1，取消时置 **NULL**（NULL 不参与唯一性，规避"取消后该格永久不可再约"）。
- `devices.status ∈ {available, borrowed, offline}`
- `bookings.status ∈ {booked, picked, returned, cancelled, expired}`

## 四、时段规则（必须定死，否则开发反复）

- 可约时段 08:00–20:00，2 小时一格，共 6 格/天/设备。
- 只支持整格预约，可连续多格；不可跨日；**边界相接不算冲突**。
- 提前 1–14 天可约，当天可约。
- 单人工单日上限 2 格（可配，防占坑）。
- 时间基准用服务器本地时区（Asia/Shanghai），单机内网场景不做 UTC 存储 + 前端转换；此决定需在文档注明，将来接外部系统时必须改。

## 五、功能需求（8 条，均带验收口径）

| 编号 | 需求 | 验收口径 |
|---|---|---|
| R01 | 设备台账：管理员维护设备基础信息与状态 | 资产编号唯一；仅当无未完成预约时允许删除设备 |
| R02 | 占用视图：员工按"日期 × 设备"看 6 格状态（空闲/已约/我的/已下架） | 视图与库内数据一致，不允许出现"显示空闲但提交被拒" |
| R03 | 预约：选设备 + 日期 + 格子，提交即生效（免审） | 50 人并发抢同一格：成功 1 单，其余收到"该时段已被占用"；**同格确认单数必须为 1** |
| R04 | 取消：时段开始前可取消，取消即释放 | 取消后同一秒内他人可成功预约同一格 |
| R05 | 取还登记：到时段可点"已取走"；归还填实际时间与备注 | 未点取走的预约到时段结束自动置 `expired`，不占用后续格子 |
| R06 | 超期与未取清单：管理员看"过时未取"和"已取未还"两列表并可强制结束 | 列表与 `bookings` 状态一致；每次处置写 `op_logs` |
| R07 | 操作留痕：所有状态变更记录 actor/时间/前后值 | 任一预约可还原完整状态轨迹；日志不可被普通管理员删除 |
| R08 | 账号管理：批量导入员工（工号/姓名/部门/初始密码），支持停用 | 停用即时生效无法登录；历史预约保留，占用的格子可由管理员释放 |

## 六、非功能约束（单机内网，写进验收）

- **部署**：1 台 2C4G，Nginx + 应用 + MySQL/PG 单实例，Docker Compose 一键起。
- **容量**：≤300 员工、≤100 台设备、≤50 并发、日预约 ≤200 单。
- **性能**：列表页 P95 < 1s，预约提交 P95 < 800ms。
- **备份**：每日全量 + binlog/归档；**上线前完成一次恢复演练并记录实测 RTO**（目标 RPO 24h / RTO 4h）。
- **安全**：密码 bcrypt/argon2；登录失败 5 次锁 10 分钟；仅内网可达；HTTPS（内部 CA 或自签）。

## 七、明确不做（附回头条件）

| 不做 | 什么条件下再考虑 |
|---|---|
| 审批流（Q3=A） | 高价值设备被"先占后不用"，管理员每周处置 > 10 次 |
| 维护/校准状态与工单（Q7=A） | 发生 1 次"维修中设备被正常预约并到场"的真实事故 |
| 扫码/智能柜（Q6=A） | "登记已取走但设备其实没被取走"的争议 ≥ 3 次/月 |
| SSO / HR 同步（Q5=A） | 员工 > 500，或离职同步每周手工 > 20 人 |
| 外部集成（Q9=A） | 需要按部门分摊成本，或需对接门禁 |
| 费用/信用/赔偿（Q8=A） | 出现真实的损坏赔偿诉求 |
| 统计看板 | 使用率类指标进入考核（当前只留基础计数，不定义口径） |

## 八、风险与人工兜底（A 方案的真实代价）

1. **设备坏了还能被约**：Q7=A 只有两态。→ **破例加 `offline`，管理员一键下架**。成本约 0.5 人日，强烈建议纳入本期。
2. **"约满但没人用"不会自动消失**：Q8=A 只记录不处理 → 靠 R06 两个清单 + 管理员手动释放，SLA 约定"每日上班后 30 分钟内清理"。**这是 MVP 最大的价值漏洞，上线前必须与管理层对齐预期。**
3. **取还是自报的**：数据可信度依赖人。争议时只能靠 `op_logs` 时间戳，无法证明物理事实。
4. **单机是单点**：备份是唯一救命线，恢复演练不通过不上线。
5. **无审批**：靠"单日 2 格上限 + 管理员黑名单"兜底，不能靠制度。
6. **账号自建**：密码重置与离岗停用必须有明确责任人，否则半年后全是僵尸账号。

## 九、仍需回答（不阻塞开发，阻塞上线）

1. 单日预约上限取 2 格还是不限？（影响 R03 校验逻辑）
2. 是否允许"当天临时加约当前时段"？允许则 R02 视图需显示"当前时段"。
3. 停用账号名下的未完成预约，是否自动释放？（默认：不自动，由管理员处置）
