## R01 · 设备台账：管理员维护设备基础信息与状态

| 项 | 内容 |
|---|---|
| 验收口径 | 资产编号唯一；仅当无未完成预约时允许删除设备 |
| 实现 | `app/db.py::create_device()` / `update_device()` / `delete_device()` / `set_device_status()`；`devices.deleted_at` 做软删除；`count_active_bookings()` 拦删除；页面 `templates/admin_devices.html`，路由 `/admin/devices` |
| 测试 | `test_delete_device_blocked_by_active_booking`（有未完成预约时删不掉）、`test_delete_device_is_soft`（删后行仍在、`deleted_at` 有值）、`test_status_change_is_translated`（状态变更写进日志） |
| 可核对证据 | 台账页对有未完成预约的设备点"删除"，返回被拒并说明是哪一单在占；`op_logs` 里 `device.delete` 保留删除前后的设备快照 |
| 未做 | 设备分组、借用频次统计；**资产编号在软删除后仍被占用**（唯一约束不排除 `deleted_at` 非空的行），编号不可复用 |
| 残余风险 | 状态只有 `available / borrowed / offline` 三态，**没有"维修中"与"校准过期"**。需求清单第七节把维护工单列为"不做"，但 R01 原文的"维护"维度其实靠 `offline` 顶替——这是降级，不是等价 |

## R02 · 占用视图：员工按"日期 × 设备"看 6 格状态

| 项 | 内容 |
|---|---|
| 验收口径 | 视图与库内数据一致，不允许出现"显示空闲但提交被拒" |
| 实现 | `app/domain/slots.py::slot_states()`（纯函数，时间由参数注入，不读系统时钟）；`app/booking_service.py::list_devices_with_availability()` 一次性取当天全部 `booked_slots()`（返回 `{slot_start: user_id}`），避免每台设备查一次；页面 `templates/devices.html` |
| 测试 | `test_slots.py` 16 项覆盖时段生成、边界相接、窗口期、优先级；`test_mine_beats_passed`、`test_others_slot_is_taken`、`test_offline_wins_over_everything`、`test_no_me_id_degrades_to_taken` |
| 可核对证据 | 四种状态优先级固定为 `offline > mine > passed > taken > free`，逐条有单测；"我的"态靠 `booked_slots` 返回的 `user_id` 与当前用户比对，不额外查库 |
| 未做 | **不显示"正在进行"的格子**：时段一开始即判 `passed`，10:17 时 10:00–12:00 显示为"已过"而非"使用中" |
| 残余风险 | 视图与库一致靠"同一份快照查询"，但页面不自动刷新——停在 09:59 的页面不会在 10:00 自己变。演示时需要手动刷新 |

## R03 · 预约：选设备 + 日期 + 格子，提交即生效（免审）

| 项 | 内容 |
|---|---|
| 验收口径 | 50 人并发抢同一格：成功 1 单，其余收到"该时段已被占用"；**同格确认单数必须为 1** |
| 实现 | `app/db.py:133` `CREATE UNIQUE INDEX uq_booking_slot ON bookings(device_id, slot_date, slot_start, active_flag)`；`create_booking()` **只 INSERT**，捕获 `IntegrityError` 转 409，不"先 SELECT 判空再 INSERT"；`app/booking_service.py::place_booking()` 做窗口期、单日上限、时段合法性校验 |
| 测试 | `test_double_booking_rejected`（同一格第二次插入被拒）、`test_boundary_adjacent_are_different_starts`（08:00–10:00 与 10:00–12:00 是两格不算冲突） |
| 可核对证据 | 手工压测 50 并发抢同一格 → 1 个 201 / 49 个 409 / 库内 1 条有效单 |
| 未做 | **压测脚本没有进仓库**，上面这行数据是手工复现的，不能一键重跑；无性能基线（P95 未测） |
| 残余风险 | 单机 SQLite 单写者模型本身保证一致性；迁 PostgreSQL 时索引语义不变，但并发行为需要重测。唯一索引把 `active_flag` 纳入键，**取消时置 NULL 才有效**——这条一旦改错，取消过的格子会永久不可再约（开发中真实踩过，回归用例 `test_cancel_releases_slot` 就是为它加的） |

## R04 · 取消：时段开始前可取消，取消即释放

| 项 | 内容 |
|---|---|
| 验收口径 | 取消后同一秒内他人可成功预约同一格 |
| 实现 | `app/db.py::cancel_booking()` 置 `active_flag = NULL`（唯一索引不约束含 NULL 的行），状态置 `cancelled`，同事务写 `op_logs` |
| 测试 | `test_cancel_releases_slot`（取消后立即再约同一格成功）、`test_force_close_rejects_finished_booking`（已取消的单不能再被处置） |
| 可核对证据 | `/bookings` 取消后立刻回 `/devices`，该格回到"可约" |
| 未做 | 没有等待队列，取消后不通知任何"想约但抢不到"的人 |
| 残余风险 | 取消与抢单落在同一秒时，结果取决于事务提交顺序，**没有公平性保证**；也不做"取消次数过多"的信用惩罚（需求清单明确排除费用/信用） |

## R05 · 取还登记：到时段可点"已取走"，归还填实际时间与备注

| 项 | 内容 |
|---|---|
| 验收口径 | 未点取走的预约到时段结束自动置 `expired`，不占用后续格子 |
| 实现 | `app/db.py::mark_picked()` / `mark_returned()`（`:1662`）／`expire_bookings()`（`:1722`）；`app/booking_service.py::pickup()` / `give_back()` 支持填**实际归还时间与设备状况**；`app/booking_api.py::expire_worker()` 每 60 秒扫一次 `booked` 且已过期的单 |
| 测试 | `test_return_releases_slot`、`test_expire_writes_log`（过期也写日志，且 actor 记为 `system:expire_worker`） |
| 可核对证据 | 登记归还时格子立刻回到"可约"；`op_logs` 里能看到 `booking.return` 的 before/after 含 `returned_at` |
| 未做 | 归还时间只校验格式与"不能是未来"，**不校验"不能早于取走时间"之外的业务合理性**；设备状况只进 `remark` 文本，不是结构化字段 |
| 残余风险 | 取还是**用户自报**的，物理事实无法证明，争议时只能靠时间戳。`picked` 的单**不会自动过期**——过期扫描只处理 `booked`，"取走不还"必须走管理员强制结束，这是最容易漏的一条 |

## R06 · 超期与未取清单：管理员看两列并可强制结束

| 项 | 内容 |
|---|---|
| 验收口径 | 列表与 `bookings` 状态一致；每次处置写 `op_logs` |
| 实现 | `/admin/overdue` 三个清单（已开始未登记 / 已取未还 / 已过期）；`app/booking_service.py::force_close()` 决定结局：`booked` 结束记 `expired`、`picked` 结束记 `returned`；`app/db.py::force_close_booking()` |
| 测试 | `test_force_close_picked_to_returned`（取走的强制结束记归还而不是过期）、`test_force_close_rejects_finished_booking` |
| 可核对证据 | 概览页把"待处置"的两类积压单独列出，**有积压才标红**——0 条也标红的话红色会被习惯性忽略 |
| 未做 | 没有定时提醒、没有超时升级、没有通知渠道（邮件/IM） |
| 残余风险 | 需求清单写的"每日上班后 30 分钟内清理"是**管理约定，系统不强制**。这是 MVP 最大的价值漏洞：约满但没人用的情况不会自动消失 |

## R07 · 操作留痕：所有状态变更记录 actor / 时间 / 前后值

| 项 | 内容 |
|---|---|
| 验收口径 | 任一预约可还原完整状态轨迹；日志不可被普通管理员删除 |
| 实现 | `op_logs(actor_id, action, target_type, target_id, before_json, after_json, ip, created_at)`；`app/db.py::_log()`（`:385`）与业务变更**同一事务**；`write_op_log()` `:429`、`list_op_logs()` `:458`、`booking_timeline()` `:496` 还原单条轨迹；**模块内不存在 UPDATE / DELETE op_logs 的函数** |
| 测试 | `test_op_log_written_with_state_change`（变更与日志同事务）、`test_op_log_never_contains_password_hash`（日志不得含密码哈希）、`test_flags_leave_audit_trail`（撤销标记也留痕） |
| 可核对证据 | `/admin/logs` 按 `target_id` 查单条预约的完整时间线；系统动作标 `system:expire_worker`，不伪装成人 |
| 未做 | 无日志导出（CSV/JSON 下载）；无哈希链或任何完整性校验；`before/after` 存 JSON 文本，不可按字段查询 |
| 残余风险 | "不可删除"是**代码层**保证（没有那个函数），不是存储层。有数据库文件写权限的人可以直接改。真要做外部稽核，需要 WORM 存储或异地日志落点 |

## R08 · 账号管理：批量导入、支持停用

| 项 | 内容 |
|---|---|
| 验收口径 | 停用即时生效无法登录；历史预约保留，占用的格子可由管理员释放 |
| 实现 | `app/db.py::create_user_if_absent()`（`:1016`，重复工号跳过且**不改密码**，所以每周导全量名单是安全动作）、`set_user_status()`（`:1064`）、`reset_user_password()`（`:1101`）；页面 `/admin/users`，支持粘贴 CSV/Excel 与中文逗号 |
| 测试 | `test_import_does_not_reset_existing_password`、`test_disable_user_keeps_bookings`、`test_weak_password_rejected`、`test_chinese_comma`、`test_missing_column_reported_with_line_no` |
| 可核对证据 | 停用后该账号登录返回 401 且提示账号已停用；名下预约仍在 `/admin/overdue` 与台账里 |
| 未做 | **停用不自动释放名下未完成预约**（需求清单第九节第 3 条，属待决策项）；不与 HR 系统同步；无登录设备管理 |
| 残余风险 | 僵尸账号靠人工清理；停用后格子仍被占，必须管理员一个个处置，批量停用 20 人时这一步会很痛 |

## 附录 A · 不变量清单

这几条是"改代码时不能破坏"的约束，各自都有回归用例：

| 不变量 | 保证方式 | 用例 |
|---|---|---|
| 同一设备同一格只有一单 | 数据库唯一索引 + 只 INSERT 不预检 | `test_double_booking_rejected` |
| 取消后该格立即可约 | `active_flag = NULL` 而非 `= 0` | `test_cancel_releases_slot` |
| 归还必须释放格子 | `mark_returned` 同时清 `active_flag` | `test_return_releases_slot` |
| 状态变更必须留痕 | 写入与日志同一事务 | `test_op_log_written_with_state_change` |
| 日志不含敏感字段 | 写入前剥离 `pwd_hash` | `test_op_log_never_contains_password_hash` |
| 导入不得重置既有密码 | 冲突时跳过而非 upsert | `test_import_does_not_reset_existing_password` |
| 时段一开始就不可约 | 纯函数按"开始时刻"判定 | `test_slot_started_cannot_be_booked` |
| 写操作必须经人确认 | 工具签名只收凭证 + 待确认动作原子 claim | `test_confirm_twice_second_time_rejected` |

## 附录 B · 待确认的三个业务口径

需求清单第九节留了三个问题，我按"最简方案"实现了，**但它们是业务决策，不是技术决策**：

| 问题 | 当前实现 | 改起来要动哪里 |
|---|---|---|
| 单日上限取 2 格还是不限 | 2 格 | `app/booking_service.py::place_booking()` 的 `max_per_day`；提示词里的数字也跟着变，需同改 |
| 当天能否约"正在进行"的时段 | 不能，含当前格 | `app/domain/slots.py::slot_states()` 的 `_slot_started()` 判定 |
| 停用账号名下未完成预约是否自动释放 | 不自动 | `app/db.py::set_user_status()` 增加一次批量取消 |

答辩时如果被问"这几个你为什么不自己定"，答案就是这张表：**技术侧已就绪，口径属于管理决策。**

## 附录 C · 非功能约束的落实情况

需求清单第六节列了部署、容量、性能、备份、安全五项。逐项对照：

| 约束 | 要求 | 实际 |
|---|---|---|
| 部署 | Docker Compose 一键起 | **未做**。当前是 `uvicorn` 单进程，无 Dockerfile |
| 容量 | ≤300 员工 / ≤100 设备 / ≤50 并发 | **未压测**。库结构与查询按此规模设计，但没有实测数据 |
| 性能 | 列表页 P95 < 1s，提交 P95 < 800ms | **未测**。无基线，无性能测试 |
| 备份 | 每日全量 + 恢复演练（RPO 24h / RTO 4h） | **未做**。数据在 `data/chat.db`，删了会重新 seed |
| 安全 | 密码哈希、5 次锁定、仅内网、HTTPS | 已做 scrypt + HS256 JWT HttpOnly Cookie + CSRF 双提交 + 5 次失败锁 10 分钟；**HTTPS 未做**（内网演示） |

这一栏坦白写"未做"，是因为它们确实没做——**演示项目不是上线系统，把"没做"说成"做了"才是真问题**。
