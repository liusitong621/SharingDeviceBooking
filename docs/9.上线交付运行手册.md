## 一、这份手册解决什么问题

系统交付后最常见的问题不是「功能不够」，而是**没人知道它现在是什么状态**：链接打开是白屏，不知道是服务挂了还是链接缺参数；问答只会复述原文，不知道是模型没配还是检索没就绪；数据看起来回到三天前，不知道是谁重置了库。

所以本手册按「先能判断，再能处置」组织：第二节说明它跑在哪里、有哪些硬约束；第三、四节给出访问与启停；第五节是可直接复制的巡检命令；第六节之后按故障类型给处置步骤。每条命令都在本次交付的沙盒环境里真实执行过，输出见第十一节。

**先读这一条**：分享链接必须**整条复制**。链接里的 `sharecode` 是访问凭据，直接访问 `https://…/login` 会返回 403 并显示「链接不完整」，那不是服务坏了。

## 二、运行环境与架构

先看清它跑在哪里、受哪些约束——后面所有「为什么不能这样」的答案都在这一节。

### 2.1 拓扑

浏览器 → 平台反向代理（校验 sharecode、终止 HTTPS）→ 单容器 uvicorn（`0.0.0.0:$PORT`，1 个 worker）→ 容器内 SQLite（`data/chat.db`）+ 进程内检索索引（`.rag_cache/`）。

沙盒**只提供一个 HTTP 端口**，没有独立的数据库、缓存或消息队列。因此数据全部落在容器内的 SQLite 文件里，检索索引也在进程内存中重建——这两点决定了后面所有的备份与重启注意事项。

CloudBase 云托管是并列的第二套形态：浏览器 → 云托管 HTTPS 网关 → 容器 uvicorn（`0.0.0.0:8080`，1 worker）→ 同样的容器内 SQLite 与进程内索引。差异在三处：端口由 `serverConfig.Port`、`EnvParams.PORT` 与 `Dockerfile` 共同固定为 **8080**（少改一处就表现为实例起来了但探针连不上）；镜像固定 `Asia/Shanghai` 时区（制度按本地时间判定 08:00–20:00，用 UTC 会整体偏 8 小时且不报错）；镜像不含 `data/chat.db`，首次启动由 `app/seed.py` 播种，**重启或重新部署回到初始演示数据**。完整参数、访问地址与重新部署步骤见仓库 README 的「部署」章节。

### 2.2 四条硬约束

| 约束 | 原因 | 违反后的表现 |
|---|---|---|
| 只能 1 个 worker | 会话互斥锁、登录限流都是进程内 dict | 并发判定静默失效，抢同一格可能成功两单 |
| 数据在容器内 | 沙盒不提供外部数据库 | 容器重建即回到发布时的快照 |
| 索引是进程内对象 | 启动时从内置制度正本与上传目录重建 | 上传制度后不重启也能生效，但重启才彻底 |
| 未配 LLM 密钥时降级 | 无外网模型凭据 | 问答只返回制度原文片段，不做归纳 |

启动入口 `scripts/serve.sh` 已把 `--workers 1` 写死，并在注释里说明原因。**不要为了「提高并发」改这个数字**，那会让第一条约束失效。

### 2.3 依赖与版本

本地与 CI 使用 `requirements.txt`（`numpy==2.5.4`，要求 Python ≥3.12）；沙盒使用 `requirements.sandbox.txt`。两份清单只有两处差异：

| 项 | 主清单 | 沙盒清单 | 原因 |
|---|---|---|---|
| numpy | 2.5.4 | 2.4.6 | 沙盒解释器低于 3.12，2.5.x 装不上（由安装日志推定） |
| faiss-cpu | 1.15.1 | 不含 | faiss 是可选导入，缺失时退化为 numpy 暴力内积 |

沙盒里去掉 faiss 是有意的：内置语料只有 9 个切片，`IndexFlatIP` 与暴力内积同为精确内积，结果一致；同时避开 faiss 与 numpy 的 C ABI 绑定（那类故障只在 import 时抛 `undefined symbol`，安装阶段看不出来）。

## 三、访问与账号

访问分两个入口，账号分两种角色；先把这一步走通，再谈功能。

### 3.1 两种入口

| 入口 | 地址 | 谁能进 |
|---|---|---|
| 员工端 | 分享链接 → `/login` | 全体员工账号 |
| 管理端 | 分享链接 → `/admin/login` | 仅 `admin` 角色 |

员工端与管理端在登录页就分开，不是同一入口按角色跳转。

### 3.2 演示账号

| 工号 | 角色 | 口令 | 状态 |
|---|---|---|---|
| `1001` | 员工 | `Staff@12345` | 正常，可直接登录 |
| `1002` | 员工 | `Staff@12345` | 正常，首次登录需改密 |
| `1007` | 员工 | — | **已停用**，用于演示停用后不能登录 |
| `admin` | 管理员 | 见交付回执 | 正常，首次登录强制改密 |

管理员初始口令**不写入仓库**，随交付回执单独提供。理由：分享链接是公开的，源码里再放一个固定管理员口令，等于把管理端一起公开。首次登录会强制跳转 `/change-password`，改完这个一次性口令立即失效。

### 3.3 登录相关的口径

- 连续 5 次口令错误锁定 10 分钟，返回 `ACCOUNT_LOCKED`（HTTP 423）。
- 登录失败不区分「工号不存在」与「口令错误」，统一返回 `INVALID_CREDENTIALS`，避免枚举工号。
- 会话令牌是 HttpOnly Cookie + HS256（`pyjwt`）。`JWT_SECRET` 未配置时会在 `data/.jwt_secret` 生成一次并复用，所以**重启不会把所有人登出**；但删掉该文件或重建容器会让现有会话全部失效。
- 本形态下 HTTPS 由平台终止，应用侧 `COOKIE_SECURE=0`（默认）。若迁到自有服务器，必须设 `COOKIE_SECURE=1`，否则 Cookie 会在明文 HTTP 上传输。

## 四、发布、启停与回滚

发布、启停、回滚是同一件事的三个方向，命令集中在这里，避免现场翻源码。

### 4.1 沙盒发布

发布动作由平台完成，不需要手工构建。当前记录：

| 项 | 值 |
|---|---|
| 沙盒 ID | `ec39cbd4437d4824af8a69fdc678e600` |
| 安装命令 | `pip install -r requirements.sandbox.txt` |
| 启动命令 | `bash scripts/serve.sh` |
| 依赖形态 | 单端口 `http-service` |

再次发布同一个目录会**覆盖**当前实例，分享链接保持不变。覆盖意味着容器内数据回到源码快照——发布前先做第六节的备份。

### 4.2 本地起服务

```bash
# 方式一：直接用封装脚本（读 PORT，默认 8000）
PORT=8000 bash scripts/serve.sh

# 方式二：指定解释器（例如复现沙盒那套依赖）
PYTHON=/path/to/python PORT=8000 bash scripts/serve.sh

# 方式三：原始命令，等价
.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

首次启动会自动建表、写入种子数据、构建检索索引。日志里出现下面三行才算真正就绪：

```
SQLite 就绪：/…/data/chat.db
检索就绪：9 个切片，向量后端 hash-local，LLM 未配置（降级模式）
Uvicorn running on http://0.0.0.0:8000
```

### 4.3 停止

前台运行时 `Ctrl+C` 即可。容器形态下停止/重启由平台控制，应用侧没有需要额外清理的常驻进程（过期扫描任务挂在 lifespan 里，随进程退出而取消）。

### 4.4 回滚

| 场景 | 做法 |
|---|---|
| 代码问题 | `git revert <commit>` 后重新发布；沙盒不保留历史版本 |
| 数据污染 | 用第六节的备份覆盖 `data/chat.db` 后重新发布 |
| 整站下线 | 用同一目录执行「取消发布」，分享链接立即失效 |

回滚代码**不会**回滚数据：`data/chat.db` 是运行期文件，不在版本控制里。这一点必须记住，否则会出现「代码回退了、脏数据还在」。

## 五、日常巡检

巡检的目标不是「看一眼」，而是用固定命令得到可比较的结果。

### 5.1 一条命令看健康

平台的 `/healthz` 是平台自己的探活（返回 `Pod alive`），**不是本应用的**。应用探针在 `/api/healthz`，且必须先拿到 sharecode Cookie：

```bash
BASE="https://device-booking-assistant.app.workbuddy.host"
LINK="$BASE/?sharecode=KGUXDCPFIW"
JAR=$(mktemp)

# 第一步：用完整链接换 Cookie（-L 跟随 302 到登录页）
curl -s -c "$JAR" -b "$JAR" -L -o /dev/null "$LINK"

# 第二步：查应用探针
curl -s -b "$JAR" "$BASE/api/healthz"
```

期望输出（本次实测）：

```json
{"status":"ok","version":"0.3.0","db":"ok","rag":"ready","llm":"fallback","chunks":9}
```

字段含义与判定：

| 字段 | 正常值 | 异常时说明 |
|---|---|---|
| `status` | `ok` | `starting` 表示 `data/chat.db` 还没建好 |
| `db` | `ok` | `missing`：数据目录不可写或库文件丢失 |
| `rag` | `ready` | `degraded`：索引没建起来，问答会退化为「没有检索到资料」 |
| `llm` | `fallback` | `configured` 表示配了模型密钥；`fallback` 是**预期状态**，不是故障 |
| `chunks` | `9` | 明显变小：制度文档被停用或上传目录丢了 |

探针刻意只返回可用性，不返回用户数、预约数等业务数据——分享链接是公开的，多一个数字就多一条泄露路径。这条约束有单元测试钉住（`tests/test_healthz.py`）。

### 5.2 巡检频次建议

| 频次 | 检查项 | 判定 |
|---|---|---|
| 每次发布后 5 分钟内 | 完整链接可打开、`/api/healthz` 为 ok | 任一不满足即回滚 |
| 每日 | 探针 `rag` 是否仍为 `ready`、`chunks` 是否异常 | 连续两次 degraded 即排查 |
| 每周 | 磁盘占用、`pending_actions` 行数、登录失败锁定记录 | 见 5.3 |
| 每月 | 备份可恢复性演练（在临时目录恢复一次并查行数） | 恢复不出来等于没备份 |

### 5.3 需要关注的三个慢增长

| 对象 | 为什么会涨 | 处理 |
|---|---|---|
| `pending_actions` | 待确认动作靠 `expires_at` 惰性过期，没有定时清理 | 超过 1 万行前加清理任务或手动删过期行 |
| `op_logs` | 只追加、没有删除入口（设计如此） | 按需归档到外部存储，不要删表 |
| `chat_sessions` / `chat_messages` | 每次提问都落库 | 演示环境可定期清空，生产环境按留存策略处理 |

## 六、数据备份与恢复

备份的关键不是备份动作本身，而是恢复时能不能对上行数。

### 6.1 备份什么

| 路径 | 内容 | 是否必须 |
|---|---|---|
| `data/chat.db` | 用户、设备、预约、日志、会话、待确认、提示词版本 | **必须** |
| `data/kb/uploads/` | 管理员上传的制度文档 | 有上传就必须 |
| `docs/4.设备借用制度.md` | 内置制度正本（RAG 语料，随代码走） | 已在版本控制里 |
| `.rag_cache/` | 索引缓存 | 不必，可重建 |

### 6.2 备份命令

WAL 模式下直接 `cp` 可能拿到不一致的快照，要先合并：

```bash
cd /path/to/SharingDeviceBooking

# 合并 WAL 并做一致性校验
sqlite3 data/chat.db "PRAGMA wal_checkpoint(TRUNCATE); PRAGMA integrity_check;"

# 用 SQLite 自带备份（在线安全，不锁死写入）
mkdir -p backup
STAMP=$(date +%Y%m%d-%H%M)
sqlite3 data/chat.db ".backup backup/chat-$STAMP.db"

# 制度文档一起打包
tar -czf "backup/kb-$STAMP.tar.gz" data/kb 2>/dev/null || true

ls -lh backup/
```

沙盒环境下无法直接登进容器，备份要从**发布源**做：本地 `data/chat.db` 就是线上快照的来源。发布前先按上面命令备份，再发布。

### 6.3 恢复

```bash
# 1) 停服务（容器形态：先取消发布，或停掉本地进程）
# 2) 校验备份可用
sqlite3 backup/chat-20261106-1030.db "PRAGMA integrity_check; SELECT count(*) FROM bookings;"
# 3) 覆盖并清理 WAL 残留
cp backup/chat-20261106-1030.db data/chat.db
rm -f data/chat.db-wal data/chat.db-shm
# 4) 起服务，看启动日志与探针
PORT=8000 bash scripts/serve.sh
```

恢复后必须验证三件事：`/api/healthz` 的 `db` 为 `ok`、`bookings` 行数符合预期、用已知账号能登录。只看「服务起来了」不算恢复成功——空库也能起来。

### 6.4 一个必须知道的边界

沙盒是**演示环境**，平台侧不提供自动备份与时间点恢复。重新发布会用源码里的 `data/chat.db` 覆盖容器内数据。所以：

- 线上产生的真实操作（新预约、新日志）**不会自动回流到本地**；
- 要保留线上数据，必须在容器被重建前导出，而当前形态没有导出入口；
- 结论：**这个部署只用于演示与验收，不要当作有数据保障的生产系统**。

这不是运维疏忽，而是沙盒形态的固有限制。真要承接到业务，需要换成带持久卷与定时备份的部署方式（见第十二节）。

## 七、常规运维操作

这些操作都有管理端入口，不需要登录服务器，也就不需要 shell 权限。

### 7.1 账号

| 操作 | 路径 | 说明 |
|---|---|---|
| 新增/导入员工 | 管理端 → 用户管理 → 批量导入 | Tab 或逗号分隔，首行表头；重复导入不重置已有密码 |
| 停用账号 | 用户管理 → 停用 | 停用**不自动释放**已有预约，格子仍被占着 |
| 重置密码 | 用户管理 → 重置 | 置回初始口令并标记 `must_change_pwd=1` |
| 改自己的密码 | 右上角 → 修改密码 | 弱口令会被拒（`WEAK_PASSWORD`） |

### 7.2 设备台账

| 操作 | 约束 |
|---|---|
| 新增设备 | 资产编号唯一，重复报 `DEVICE_EXISTS` |
| 上架/下架 | 下架后整列时段锁死，API 同样拒绝（`DEVICE_OFFLINE`） |
| 删除设备 | 软删除；有未完成预约时拒绝（`DEVICE_HAS_ACTIVE_BOOKINGS`），历史预约仍能 JOIN 出设备名 |

### 7.3 制度文档与索引

管理端 → 制度文档：

1. 上传只支持 `.md` / `.txt`，单文件 ≤512KB，PDF 会被拒（`KB_UPLOAD_INVALID`）。
2. 上传后**无需重启**即可检索到新内容，热更新由 `rag.rebuild()` 完成。
3. 「停用」会让文档退出索引，但保留 `last_chunk_count` 供判断影响面；内置文档只能停用不能删除（`KB_DOC_BUILTIN`）。
4. 重建失败时旧索引保留（`KB_REBUILD_FAILED`），不会出现「重建到一半检索全空」。

内置语料优先读 `docs/manuals/`；该目录被文档整理移走时，`app/rag.py` 会自动回退到 `docs/` 根目录，并按 `*设备借用制度*.md` 只挑制度正本（避免把调研报告一起切进索引）。所以给 `docs/` 文件加编号前缀不会再让索引建空；但仍要确认至少有一份文件名含「设备借用制度」的 md 存在。若 `rag` 变成 `degraded`，先看启动日志里是否报「找不到阶段 1 模块」——云托管镜像必须同时带上 `scripts/stage1_rag_prototype.py`，索引构建失败会被 `warmup()` 按设计吞掉，服务照常 200，只有探针的 `chunks=0` 能看出来。

### 7.4 提示词版本

管理端 → 提示词：

- 保存即发布，版本号只增不减；同一版本号不能覆盖（`PROMPT_VERSION_CONFLICT`）。
- 「回滚」是**用旧内容发一个新版本**，不是把版本号退回去。
- 未知占位符（如 `{max_slot}` 少一个 `s`）保存时直接报错（`PROMPT_INVALID`）；缺 `{today_hint}` 只是警告，渲染时会自动追加。

### 7.5 审计与标记

管理端 → 审计：按工号/关键词/日期筛 run，点进去看每一轮的工具调用与参数。标记「有问题」只写 `agent_run_flags`，**不改原始轨迹**——这是审计可信的前提，验证时不要找「修改记录」功能，它故意不存在。

## 八、日志与监控

这个形态只有 stdout 一种日志，所以三个关键信号必须记牢。

### 8.1 日志在哪

只有 stdout。沙盒形态下由平台收集，本地运行时直接打在终端。格式：

```
2026-11-06 10:18:32,149 INFO    app.main | SQLite 就绪：/…/data/chat.db
2026-11-06 10:18:32,226 ERROR   app.main | 检索未就绪：RuntimeError: 没有找到任何制度文档
INFO:     127.0.0.1:51342 - "GET /api/healthz HTTP/1.1" 200 OK
```

### 8.2 三个关键信号

| 信号 | 含义 | 该做什么 |
|---|---|---|
| `检索未就绪` + `ERROR` | 索引没建起来 | 查制度正本 md 是否存在、`scripts/stage1_rag_prototype.py` 是否在镜像里、上传目录是否可写 |
| `LLM 未配置（降级模式）` | 没有模型密钥 | 预期状态；要完整问答需配 `LLM_API_KEY` |
| 大量 `401` / `423` | 口令错误或账号被锁 | 查 `users.failed_count` / `locked_until` |

### 8.3 告警建议

当前形态没有内置告警。最小可用方案是外部定时任务打探针：

- 探针返回非 200，或 `status != ok` → 告警；
- `rag != ready` 连续两次 → 告警；
- `chunks` 比基线（9）下降 → 提示「制度文档可能被停用」。

## 九、故障处置

按现象查，不要按代码查——运维现场没有时间读源码。

| 现象 | 先判断 | 处置 |
|---|---|---|
| 打开显示「链接不完整」 | 是否直接访问了子路径或截断链接 | 用整条分享链接重新打开 |
| 任意页面 403 | 缺 sharecode Cookie | 先访问完整链接换 Cookie，再进子路径 |
| 登录返回 401 | 口令错误或账号不存在 | 用 3.2 的演示账号；仍失败查 `failed_count` |
| 登录返回 423 | 连续 5 次失败被锁 | 等 10 分钟，或管理端重置口令（会清零计数） |
| 登录返回 403 `ACCOUNT_DISABLED` | 账号被停用 | 管理端启用；注意停用不释放已占格子 |
| 问答只复述原文 | `llm` 为 `fallback` | 预期行为；要归纳式回答需配模型密钥 |
| 问答说「没有检索到资料」 | `rag` 为 `degraded` 或 `chunks=0` | 恢复制度正本 md / 补齐阶段 1 脚本后重建索引 |
| 页面 500 且日志有 `no such column` | 库结构比代码旧 | 用备份恢复，或删除库重启重建（会丢数据） |
| 重启后所有人被登出 | `data/.jwt_secret` 丢了或被重建 | 属预期；重新登录即可，长期稳定需固定 `JWT_SECRET` |
| 数据回到发布时 | 容器被重新发布 | 用备份恢复；先确认没有别人在操作 |

## 十、安全边界

先承认暴露面，再谈加固；藏起来的风险不会因为不写而消失。

### 10.1 这个部署的真实暴露面

分享链接 + `sharecode` 就是访问凭据。拿到链接的人可以：

- 用 `1001 / Staff@12345` 登录员工端，看到全部设备与预约（合成数据）；
- 尝试猜管理员口令（有 5 次锁定，但不能阻止长期尝试）；
- 读取制度问答返回的内容。

不能做的：删改审计轨迹（没有删除函数）、越权操作他人预约（`BOOKING_FORBIDDEN`）、直接读数据库（容器内文件不对外）。

### 10.2 上线前必须完成的三件事

| 事项 | 状态 | 说明 |
|---|---|---|
| 管理员口令改为一次性强口令 | **已完成** | 首次登录强制改密；明文只在交付回执里 |
| 删除随源码上传的 `data/.jwt_secret` | **已完成** | 避免开发密钥带上线，容器首次启动自行生成 |
| WAL 合并后发布 | **已完成** | 否则容器里的库可能缺最后几条写入 |

### 10.3 迁到生产前还缺什么

| 缺口 | 影响 | 建议 |
|---|---|---|
| 无自动备份 | 容器重建即丢数据 | 挂持久卷 + 定时 `.backup` + 异地留存 |
| 无 HTTPS 配置示例 | 自有服务器上 Cookie 会明文传输 | 前置 Nginx/Caddy 终止 TLS，设 `COOKIE_SECURE=1` |
| 单实例 + 进程内锁 | 不能横向扩容 | 换数据库行锁或 Redis 锁，索引外置到 pgvector |
| 演示账号与口令仍在库里 | 公开链接下可被登录 | 删除 `app/seed.py` 的默认账号，改为首次部署强制初始化 |
| 无压测与容量数据 | 不知道 50 人同时抢格的真实上限 | 用真实 HTTP 压测补 P95 与错误率 |
| 未做数据保留策略 | `chat_messages` 会一直涨 | 按留存期归档或清理 |
