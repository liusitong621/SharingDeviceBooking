# 检索质量评测

> 这份报告由 `scripts/eval_rag.py` 生成，表里每个数字都是跑出来的。
> 换切片、换分词、换融合参数之后重跑，数字会跟着变——**报告里不写死任何结论性数字**。

## 怎么复现

```bash
python scripts/eval_rag.py                       # 只看表
python scripts/eval_rag.py --md docs/检索评测.md  # 重新生成本报告

# 配上真实 embedding 后端再跑一遍，向量那一路的数字才有意义：
EMBED_BACKEND=api LLM_API_KEY=sk-xxx python scripts/eval_rag.py
```

## 评测设置

- 语料：`docs/manuals/设备借用制度-v1.md`，切成 **9 个切片**（500 字 / 80 字重叠），当前切法下一章一片
- 问题：**20 条**，分三档——字面 12 条、口语 6 条、跨章 2 条
- 指标：Hit@1 / Hit@3 / MRR；线上只把 top3 交给模型，所以 Hit@3 是**有效召回的上限**
- 向量后端：`hash-local`（未配置密钥时的本地哈希向量，只有字面重合，没有语义）
- 三路共用同一份切片与分词，差异只来自融合策略
- 融合权重：BM25 1.0 / 向量 0.1（与线上 `app/rag.py::fusion_weights()` 一致）

## 结论

混合检索的 Hit@3 与最好的一路持平（85%）。**这不是 RRF 没用，是两路信号同源**：
当前向量后端是本地哈希（字符 n-gram），它和 BM25 一样只在做字面匹配，
两路看到的是同一批特征，融合自然提不出新的召回。

持平本身就是降级后端下的目标：向量路没有独立信息，能做到的上限就是"不拖后腿"。
等权融合做不到这一点（会掉到 75%），所以线上按后端降了权——见「三处改动」一节。
要验证混合真正能提升，必须换成真实 embedding 后端，让向量那一路负责同义改写、
BM25 负责编号与术语；那时两路才有互补，等权才成立。

真正值得看的是档位差异：字面档 100%、口语档 50%。
口语档掉分，说明**换一种说法就找不到了**——这正是关键词检索的固有短板，
也是配真实 embedding 后最该被验证的地方。答辩时这组对比比一个总分更有说服力：
它指出了系统的能力边界在哪，而不是只说"效果不错"。

## 三处改动，都是被这 20 条问题逼出来的

跑一次出个分数只是体检。这一版检索改了三次，每次改完都重跑同一组问题：

| 改动 | 起因 | 复测结果 |
|---|---|---|
| 停用词补疑问词 | Q01「几点到几点」里的"点"命中了「到达预约时段后」 | MRR 0.72 → 0.74；Hit@3 不变 |
| 标题权重 ×2 | 298 字的「二、可预约时段」被 167 字的短切片挤到第 4 位 | BM25 字面档 92% → 100%，Q01 进前三 |
| 降级后端向量降权 | 等权融合把 Hit@3 从 85% 拉到 75% | 75% → 85%，回到与单路持平 |

第二处值得单独说：它修好了 BM25，却让**融合**从 80% 掉到 75%。
标题重复同时放大了向量路的偏差，两路一起错时 RRF 会互相加固。
如果只跑单路、不复测融合，这一步会被当成纯改进——第三处改动正是被这次退步逼出来的。

这三行数值是同一份语料、同一组问题上逐步测出来的，脚本不重算它们；
上方的结果表才是当前代码的实测值。

## 这份评测没覆盖什么

- **生成质量**：只测召回，没测模型是否忠于资料、是否编造。那需要跑模型，而无密钥时走的是「检索 + 原文直出」的降级路径，测出来的不是线上行为。
- **拒答**：语料里没有的问题应该回答"资料未收录"。当前问题集全部有答案，没有覆盖"问了个制度没写的事"这种情况。
- **规模**：9 个切片、20 条问题，够回答"两路有没有互补"，不够说明"换成 200 份制度还准不准"。真实语料下需要重新标注并扩大问题集。
