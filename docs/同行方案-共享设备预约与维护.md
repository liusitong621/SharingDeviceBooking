## 二、重点案例详析

### 案例 1：NUCore Open —— 生产级「核心设施」标杆（最贴近的组织样板）

**基本信息**：西北大学核心设施管理软件的开源版本，2011 年起由 Wyeworks/TXI 持续维护，Heroku 有在线 demo，Docker 本地一键起步。

**核心能力**（README 及文档可确认）：
- 完整的**多角色模型**：Admin / PI（课题负责人）/ Normal User / Facility Staff / Facility Director，与练习中「平台主任—质控负责人—课题组代表」三方结构直接对应。
- **插拔式引擎（Rails engines）**：信用卡与采购订单（c2po）、电源继电器控制（dataprobe）、多账户分摊计费（split_accounts）、LDAP/SSO 认证、测序订单表单等——按学校需要启用。
- 专门的 `instrument_pricing.md` 定义**仪器计价模型**（对练习中「收益要扣除维护及人工复核成本、不能把节省工时当现金回款」有直接参考价值）。

**对本项目的启发**：
- REQ-3（验收标准未定义）：NUcore 的启示是**把验收口径做进系统结构**——设施主任、质控、用户三类角色各自有可见的验收界面（订单、报告、计费明细），而不是口头约定。
- REQ-4（交接无记录）：Facility Staff 角色即「操作员」，其操作天然落在系统单据上，交接班从「人盯人」变成「单据状态」。
- 计费与成本核算模块提示：首期试点即使不做真结算，也应把「使用时长 × 维护占时」记录下来，才能算清 8 万预算的收益口径。

**注意事项**：Rails 单体 + 可插拔引擎的架构，适合长期演进；直接整套引入对一个 3 台设备的试点过重，建议**只借鉴其角色/计费模型**。

### 案例 2：YaleSTC/reservations —— 规则化借还与清单化交接

**基本信息**：耶鲁大学科技与创新部门的设备借还系统，MIT 许可，138 star（本主题下 star 最高），2020 年后停更但功能完整。

**核心能力**（README 原文要点）：
- 设备库存管理：序列号、手册及其他文档随设备存档；
- 带图片的可检索设备目录；
- 「按你设定的规则」提前预约；
- **强制执行「谁能预约什么设备、能约多久」**（enforce rules on who can reserve what equipment, and for how long）；
- 借还管理，**每台设备可有独立的检查清单**（unique checklists for each item）。

**对本项目的启发**：
- REQ-2：资质校验不需要自建——「用户 × 设备」的授权矩阵 + 有效期就是现成模式；
- REQ-4/REQ-5：「借还即清单」正是练习中「班前确认—使用—班后确认—遗留问题」要的结构化形态；每台光谱设备的检查清单可以承载「标定状态确认」一项；
- 「文档随设备」直接回应 f34-f39（现场手记应绑定设备/班次/事件，而不是留在便利贴和群聊）。

**注意事项**：2020 年停更，评估时需确认漏洞修复与依赖升级情况；作为**设计参照**而非直接部署对象更合适。

### 案例 3：labqueue —— 预约并发与维护窗口的数据层设计（证据文化范本）

**基本信息**：一个刻意用来测量并修复数据库缺陷的仪器预约 API；.NET 10 + PostgreSQL 17，MIT 许可，2026-09 活跃，有在线 demo 与 Grafana 看板。

**核心能力**（README 原文要点）：
- **认证门槛 + 维护窗口**是一等公民：预约按五条规则顺序校验——资源存在且可用 → 时间窗合法 → **持证人持有效认证** → **不与维护窗口重叠** → 无已确认预约重叠（最后一条由数据库强制）；
- 时间区间用 PostgreSQL `tstzrange` 单列存储 + GiST 排他约束，50 个并发抢同一时段从「50 个全部成功」修复为「1 个成功、49 个 409」；
- 作者诚实记录了**未解决的维护窗口竞态**（跨表无法用排他约束，需 trigger 或 SERIALIZABLE），并公开了全部测量数据、查询计划和压测脚本。

**对本项目的启发**：
- REQ-1（预约状态与维护/标定状态不同步）：**把「维护/标定窗口」建模为与预约同级的排他资源**，从数据层消灭「维护中被预约」；
- REQ-2：预约校验链的顺序（先查认证、再查维护、最后才查冲突）就是人工复核前的机器预审逻辑；
- REQ-3（验收标准未定义）：该项目示范了如何用**可复现的测量数据**定义验收（如「并发 50 预约同一槽位，仅 1 单成功」），可直接借用到试点验收标准；
- REQ-6：诚实的「已知限制」章节是数据质量与降级预案的写法样板——首期上线前应同样明示哪些竞态未闭合、降级到什么程度。

**注意事项**：维护窗口竞态未闭合这一点，恰说明本项目**不能把「冲突为零」完全押在数据库约束上**，仍需操作员人工兜底（与 REQ-2 红线一致）。

### 案例 4：Calibra Fácil —— 标定/维护流程与记录留痕

**基本信息**：面向 ISO/IEC 17025 标定实验室的管理软件，源自巴西 accredited 实验室商用 SaaS 的开源化，TypeScript/Hono/Postgres，MIT 许可，2026-10 活跃（提交密集）。

**核心能力**（README 原文要点）：
- **标定工作流**：草稿 → 执行 → 技术审核 → 批准，角色分离，批准版本不可变，修订保留历史；
- **参考标准有效期控制**、人员资质、校准间隔分析、OOT（超差）通知；
- 离线桌面端：外出/现场作业时本地 SQLite + outbox 冲突解决，恢复网络后同步——**正好对应练习中「现场手记断网/换班场景」**；
- 客户门户：客户可查看仪器、到期日与证书。

**对本项目的启发**：
- REQ-1：「标定后仍误标可预约」的解法 = **状态机显式建模**：维护中 → 待标定 → 标定中 → 可预约，每次流转留审批记录，而非一个可手改的布尔字段；
- REQ-4/REQ-5：不可变批准版本 + 修订历史 + outbox 离线同步，是「交接记录可核验」「手记随文档移交」的工程化答案；
- REQ-3：「标定间隔分析」提供量化验收思路（如标定及时率）。

**注意事项**：对标定合规（证书签发、GUM 不确定度）能力远超本项目需要，**只需取其状态机与留痕模式**。

### 案例 5：Louez —— 库存 + 预约 + 合同 + 结算的完整闭环

**基本信息**：开源设备租赁平台（Next.js 16 + MySQL，Docker 一条命令部署，自带数据库与对象存储），AGPL-3.0，58 star，2026-10 活跃，1200+ 提交。

**核心能力**（README 原文要点）：
- 库存（含图片、价格档位、**库存跟踪**）、预约（状态流转）、周/月日历视图、客户档案、**自动生成 PDF 合同**、邮件确认与提醒、团队角色权限；
- 店面实时可用性展示；统计看板含**占用率洞察**（occupancy insights）；
- AI 顾问/AI 接单员为增值模块，可不用。

**对本项目的启发**：
- REQ-4：「取用—归还」状态机 + 每单 PDF 合同，把「谁在什么时间拿走什么、状态如何」变成可归档单据；
- 「占用率统计」直接对应练习中**有效使用率 51% → 68%** 的度量需求——首期即使只做 3 台设备，也应保留此类统计原语；
- 邮件确认/提醒机制可改造成预约确认与爽约预警（结合案例 7 的信用积分）。

**注意事项**：**AGPL-3.0 是强copyleft**——若二次开发后对外提供网络服务，须开源修改部分。对 8 万元预算的内部项目风险可控，但法务口径需业务方确认；另外它本质是商业租赁软件，计费/店面能力对本项目属过剩功能。

### 案例 6：django-lab-inventory —— 轻量库存基线

**基本信息**：学术实验室（meliza lab）的库存管理系统，Python/Django，BSD-3-Clause，51 star，持续维护。

**核心能力**：物品入库、位置、借用记录等实验室库存核心模型，代码量小、结构清晰，适合快速通读改造。

**对本项目的启发**：
- REQ-6：作为「数据质量基线」——设备主数据（编号、位置、状态、关联文档）的最小可用 schema；
- 适合作为 3 台设备试点的**数据层脚手架**，后续再按 labqueue 的思路加固并发约束。

**注意事项**：无预约调度能力，需自行扩展。

### 案例 7：校园实验室设备预约（Spring Boot + Vue）—— 爽约治理的量化手段

**基本信息**：Spring Boot + Vue 3 + MySQL 的校园设备预约系统，MIT 许可，支持设备预约、**信用积分**、实时通知。

**核心能力**：预约 + 信用积分体系 + 消息推送。

**对本项目的启发**：
- 直接对应练习痛点：**爽约率 16% → 6%** 与「预约满了但实际没人用」。信用积分（违约扣分/守约加分，低分限制预约）是同行中被广泛采用、且可在 Excel/轻量系统中先落地的治理机制；
- 实时通知可承接 REQ-2 的「冲突提醒」（注意练习明确通知内容要进交接记录，而非只发短信/微信——见 f31）。

**注意事项**：star 少、属课程/毕业设计级项目，**借鉴机制而非工程质量**；信用规则涉及用户权益，需业务方确认权重（FDE 不代定）。

### 案例 8：RFIDAccessSystem —— 物理权限联动（远期选项）

**基本信息**：Python + Raspberry Pi + RFID，用在线预约控制房间与设备门禁/电源，GPL-3.0，2020 年停更。

**核心能力**：预约通过 → RFID 授权开门/通电；把「谁能用」落到物理层。

**对本项目的启发**：
- REQ-2 的终极形态（f40「未培训人员不能上机」）：系统预约 + 物理门禁双因子，彻底消除「预约了但人不对」；
- 对高价值光谱设备，可作为试点验证后的**二期增强**，不属于首期必要范围。

**注意事项**：涉及硬件改造与实验室电路安全，**超出 8 万预算与首期范围**，仅列为演进方向；停更项目需重新评估。

### 案例 9（反面对照）：iHa0/InstrumentReservation —— 没有系统时会发生什么

**基本信息**：基于 Selenium 的「实验仪器自动抢预约」脚本，11 star。

**现象**：研究者写脚本定时抢号——这正是「每月 900 次预约、操作员每周 8 小时协调时间」与「预约满但没人用」并存的数字化副产品：**当官方渠道不能满足需求（合适时段稀缺、短实验无槽位），用户会自己造工具**。

**对本项目的启发**：
- 论证 REQ-1/REQ-5 的紧迫性：当前状态下，协调成本已高到用户愿意用脚投票；
- 反向提示：上线新系统时若时间槽设计不改善「短实验无合适槽位」，脚本抢约会迁移到新系统，冲突与爽约依旧——**槽位粒度设计须纳入试点范围**。

### 案例 10（基线对照）：Excel-Equipment-Booking-System —— 零代码方案

**基本信息**：用 Excel 模板管理共享设备与班组级预约，0 star 但 2026-08 仍在更新。

**对本项目的启发**：作为**成本对照基线**——若首期只求「预约状态与维护状态同步 + 记录留痕」，结构良好的 Excel + 规范流程可能以接近零成本达成大部分 REQ-4/REQ-5 目标；自建/引入系统的增量价值必须明显超过此基线，才符合 8 万预算的收益口径（f03）。

## 四、对本项目的落地建议（供业务方决策，不代定权重）

1. **架构路线**：不建议整套引入任何开源系统（NUCore 过重、Louez 许可证偏强、其余 star 偏低）。建议以 **django-lab-inventory 类轻量 schema 起步**，按 **labqueue 的数据层模式**（维护/标定窗口与预约同级排他 + 规则顺序校验）实现核心不变量，按 **Calibra Fácil 的状态机与留痕模式**实现交接与手记。
2. **首期范围锚点**（对应 f05：历史资料回放 → 小范围并行试点）：回放阶段即可复用同行模式验证「维护窗口排他」在历史数据上能拦住多少误标；并行阶段保留人工复核为唯一生效路径。
3. **验收口径建议**（待三方确认）：直接借用可量化指标——冲突预约拦截率（目标接近 labqueue 的「重叠确认对为 0」）、误标可预约次数、爽约率（16% → 目标值）、记录完整率（班前/班后/遗留三项确认留痕率）。
4. **预算视角**：8 万预算内，开源方案的成本主要在集成与培训（与 f03 一致）；Excel 基线（案例 10）应作为对照组先跑一轮，用数据证明系统化的增量价值。
5. **许可证提示**：若最终选型涉及 AGPL（Louez）或 GPL（RFIDAccessSystem）组件，需先过法务；MIT/BSD 组件（NUCore、labqueue、Calibra Fácil、django-lab-inventory、Techd81）无此顾虑。

## 五、风险与注意事项

- **star 数 ≠ 适用性**：本主题高 star 项目如 rinvex/laravel-bookings（465★）已标记 ABANDONED；反之 labqueue、Calibra Fácil star 低但工程严谨、更新活跃。选型应以「与需求的映射度 + 维护状态」为准。
- **停更项目**（YaleSTC/reservations 2020、rick1924 2020、lyle/gear 2013）仅作设计参照，直接部署需自行承担安全与依赖升级。
- **并发没有银弹**：labqueue 自述跨表维护窗口竞态未闭合——本项目同样要把「冲突为零」目标拆成「数据库能保证的」+「人工复核兜底的」两层，并在验收标准中分开表述。
- **用户会用脚投票**：iHa0 抢约脚本说明，若新系统不改善时段粒度（短实验槽位）与可用性，灰色工具会迁移而非消失。
