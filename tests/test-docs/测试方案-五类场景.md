> 被测系统：SharingDeviceBooking（FastAPI + SQLite + 原生前端 + 自研 Agent Harness）
> 需求基线：`docs/一页纸需求清单-MVP-v1.md`（R01–R08 及 §六 非功能约束）
> 方案版本：v1.0　|　编制日期：2026-11-06
> 执行器：`scripts/test_scenarios.py`　|　机器可读结果：`output/testing/results.json`
> 每场景的过程记录：`docs/testing/测试过程-{1…5}*.docx`

## 一、这份方案要回答什么

项目已有 130 项单元测试和 R01–R08 需求自检，但它们回答的是「函数有没有抛异常」。评审更常问的是另一类问题：

- 「50 人同时抢同一格，到底成了几单？」
- 「第 15 天是真的被拒，还是前端把日期框灰掉了？」
- 「连续输错 5 次密码，锁了没有、锁多久？」
- 「数据库坏了，页面是 500 还是能继续用？」

这些问题要的是**可核对的数值**，不是布尔值。本方案把基线里每个写死的数字做成一条带观测值的断言，按**正常 / 边界 / 对抗 / 权限 / 故障**五类场景组织，共 30 条用例；每条都记录「输入 → 逐步观测 → 实测值 → 判定 → 耗时」，结果由执行器真实跑出，文档生成脚本只消费结果文件，不重新编数字。

## 二、测试环境与可比性边界

| 项 | 值 |
|---|---|
| 解释器 | Python 3.13.12（CI 另跑 3.12 / 3.13 两端） |
| 数据库 | SQLite 临时库，每个场景独立 `tempfile.mkdtemp()`，互不污染 |
| 时区 | 服务器本地时区（Asia/Shanghai，UTC+8） |
| 并发模型 | 单进程 `asyncio` 协程 |
| 执行入口 | `.venv/bin/python scripts/test_scenarios.py` |
| 回归证据 | `python -m unittest discover -s tests -p <文件> -k <关键字> -q` |

**必须写清的三条边界，避免把这份报告当成压测结论：**

1. 50 并发是**同一进程内 50 个协程**打服务层，验证的是唯一索引在并发写下的正确性；它不是 50 个进程或 50 台机器，不能据此承诺容量。基线 §六 的「≤50 并发」是部署容量目标，需要真实 HTTP 压测另测。
2. 800 ms 取自基线「预约提交 P95 < 800 ms」。本机 SQLite 单机实测只在同机可比；本方案记录的是**单次样本的总耗时**，不是统计意义上的 P95（后者需要至少 100 次样本取分位数）。
3. 故障场景里标注「回归」的步骤由既有单元测试提供证据，只作为降级路径的佐证，**不计入 30 条量化用例**。

## 四、场景设计与用例矩阵

### 4.1 正常场景（N，6 条）

**目标**：证明主流程在预期输入下跑得通，且基线的性能与唯一性指标有实测值。
**风险**：「功能能点」不等于「并发下不超卖」，50 人抢同一格是 R03 唯一的硬指标。
**通过门槛**：6/6；50 并发成功 1 单、同格有效占用 = 1、全程 < 800 ms；视图差异 = 0。

| 编号 | 输入 | 预期（量化） | 判定依据 | 关联 |
|---|---|---|---|---|
| N01 | 08:00–20:00 / 2h 一格 | 6 格，首 08:00、末 20:00 | 格数与首尾时刻 | §四 |
| N02 | 1001 / D+3 / 08:00+10:00 | 2 单，库内 2 格，视图 mine 2 格 | `count` / `count_bookings_on_date` / `device_slots` | R02、R03 |
| N03 | 取消后 1002 重约同格 | 1 单成功，同格有效占用 1 | `booked_slots` 长度 | R04 |
| N04 | booked→picked→returned | 轨迹 ≥ 3 条，`returned_at` 非空 | `booking_timeline` | R05、R07 |
| N05 | 造 1 个占用后比对 | 6 格视图差异 0 | 集合异或大小 | R02 |
| N06 | 50 协程 / 同设备同日 12:00 | 成功 1、拒绝 49、占用 1、< 800 ms | 结果分类 + 唯一索引 + 计时 | R03、§六 |

### 4.2 边界场景（B，6 条）

**目标**：每个阈值的两侧各取一个值，确认拒绝发生在正确边界上、且理由可区分。
**风险**：边界写错通常不报错，只是悄悄多约一天或多放一个格子，用户很难发现。
**通过门槛**：6/6；+14 合法 / +15 拒绝；第 3 格拒绝后配额仍为 2；+5 分钟接受 / +6 分钟拒绝。

| 编号 | 输入 | 预期（量化） | 判定依据 | 关联 |
|---|---|---|---|---|
| B01 | D+0 / D+14 / D+15 / D-1 | 前两合法，后两分别报超窗/过去 | `check_date` 返回值与原因 | §四 |
| B02 | 6 个整点 + 6 个非法起点 | 非法值 6/6 报 `INVALID_SLOT` | 错误码 | §四 |
| B03 | 先占 2 格再约第 3 格 | `QUOTA_EXCEEDED`，配额仍 2 | 错误码 + 回库计数 | §四 |
| B04 | +5min / +6min / 空值 | 接受 / `INVALID_RETURN_TIME` / 回落 | 返回值与错误码 | R05 |
| B05 | 伪造 10:00:00 约 10:00 格 | `state=passed`，报 `DATE_IN_PAST` | 纯函数状态 + 下单结果 | §四 |
| B06 | 10:00 与 12:00 分属两人 | 两单共存，取消后同格可再约，占用 2 | 唯一索引键为 `slot_start` | R03、R04 |

### 4.3 对抗场景（A，6 条）

**目标**：恶意或异常输入不能写坏数据、不能重复建单、不能把内部错误暴露给用户。
**风险**：智能体的工具参数来自模型输出，等于把不可信输入直接接到写操作前面。
**通过门槛**：6/6；重复确认 0 重复单、他人凭证 0 次有效消费、注入串 0 副作用。

| 编号 | 输入 | 预期（量化） | 判定依据 | 关联 |
|---|---|---|---|---|
| A01 | 同一 `vid` 连点 2 次 | 第 2 次返回空，最终 1 单 | 原子 `UPDATE` 的 `rowcount` | R03 |
| A02 | 1002 消费 1001 的 `vid` | 返回空且原主凭证仍可用 | 归属条件在 SQL 内 | R03 |
| A03 | 4 组非法 JSON 参数 | 解析层拦下，走已登记错误码 | `JSONDecodeError` / `ERROR_TABLE` | 安全 |
| A04 | 空串 / 500 字 / 501 字 | 空与 501 拦下，500 放行 | `MAX_QUESTION_LEN = 500`，校验为 `>` | 安全 |
| A05 | 3 组 SQL 注入与 XSS 文本 | 0 异常、0 副作用 | 行数与设备表条数前后一致 | 安全 |
| A06 | 过期 1 张确认卡 / 非法会话标识 | 两次确认均被拒，扫描标记 ≥1 条 | `decide_pending` 的 `expires_at > now` | R03 |

> A06 的一处实现细节值得留档：过期判定**不在** `consume_validation`，而在 `decide_pending` 的 `WHERE` 条件里。方案初稿按前者设计，实测发现该 SQL 只检查 `consumed_at IS NULL`，于是改成测真正生效的那条路径——这是「跑一遍」相对「读代码想当然」的价值。

### 4.4 权限场景（P，6 条）

**目标**：证明权限判定在服务层与路由依赖上，而不是只靠前端隐藏按钮。
**风险**：前端隐藏 ≠ 后端拒绝；有人直接调接口时，越权改设备状态就是真实事故。
**通过门槛**：6/6；4 类越权全部拒绝；停用账号即时失效；失败 5 次锁 10 分钟；日志 0 密码哈希。

| 编号 | 输入 | 预期（量化） | 判定依据 | 关联 |
|---|---|---|---|---|
| P01 | GET `/api/devices` 无 cookie | 401 `UNAUTHORIZED` | `current_user` 依赖 | §二 |
| P02 | 1002 取消 1001 的单 | `BOOKING_FORBIDDEN`，原单不变 | 错误码 + 原单状态 | §二 |
| P03 | 员工执行 `force_close` | `FORBIDDEN`，管理员可处置 | 角色判定 | R06 |
| P04 | 员工调管理员路由 | `FORBIDDEN`，设备状态未变 | `admin_user` 依赖 | §二 |
| P05 | `set_user_status(1002, disabled)` | `ACCOUNT_DISABLED`，历史单保留 | 登录结果 + 预约计数 | R08 |
| P06 | 连续 5 次错密码 | `ACCOUNT_LOCKED`，日志无 `pwd_hash` | 错误码序列 + 日志扫描 | §六 |

### 4.5 故障场景（F，6 条）

**目标**：上游或本地数据坏掉时系统降级而不是 500，且旧数据不被破坏。
**风险**：降级最怕「静默成功」——页面看起来正常，索引其实已被清空。
**通过门槛**：6/6；6 类故障均有明确回落路径；旧索引 chunks 不减；坏 JSON 不抛异常。

| 编号 | 故障注入 | 预期（量化） | 判定依据 | 关联 |
|---|---|---|---|---|
| F01 | 提示词读库失败 | 回落内置模板，不 500 | 回归 + 模板长度 > 100 字 | 可用性 |
| F02 | 模板含未知占位符 `{max_slot}` | 保存被拦（≥1 条错误），运行回落 | `validate_template` + 回归 | 可用性 |
| F03 | 停用全部文档后 `rebuild` | 抛错但**旧索引保留** | `keep_old=True` 回归 | 可用性 |
| F04 | `before` / `summary_json` 坏 JSON | 降级显示，不抛异常 | `_diff_brief` 返回字符串 + 回归 | R07 |
| F05 | 筛选框 `date_from='不是日期'` | 退化为不筛，不 500 | `list_runs` 返回列表 + 回归 | R07 |
| F06 | LLM 超时 / 上游 5xx / 检索不可用 | 3 类明确错误码，错误回填重想 | `ERROR_TABLE` + Harness 回归 | 可用性 |

## 五、执行与判定规则

**复现命令**（项目根目录）：

```bash
./scripts/verify.sh                              # 130 单测 + R01–R08 需求自检
.venv/bin/python scripts/test_scenarios.py       # 30 条量化用例 → output/testing/results.json
.venv/bin/python scripts/render_test_docs.py     # 由结果生成 5 份过程 docx 与图
```

**单条用例判定**：`passed` 由断言计算，不是人工勾选；观测值、逐步记录、耗时一起写入 `results.json`。用例自身抛异常算 FAIL，并把异常原文写进 `observed`，不吞。

**场景判定**：该场景 6 条全 PASS 才算通过；任一 FAIL 时保留其余用例的观测数据，便于定位是哪一步先偏。

**总体判定**：30/30 为通过；若低于 100%，必须逐条列出失败用例编号、实测值与缺陷处理结论，不能以「大体通过」结案。

**性能判定**：N06 的全程耗时与 800 ms 比较；未达标单独记一条，不因功能断言全过而略过。

**回归证据**：故障场景里 `Ran N tests → OK` 属于佐证，写入过程文档，但不折算成量化用例数。

## 八、没覆盖什么（不要拿这份报告去承诺）

1. **真实 HTTP 压测**：50 协程走服务层，没有经过 uvicorn / Nginx / 网络栈，也没有多进程竞争。基线「≤50 并发、日预约 ≤200 单」的容量结论仍需单独压测。
2. **P95 的统计口径**：只测了一次，不是分位数。列表页 P95 < 1s 同样未测。
3. **浏览器端到端**：没有 Playwright/Selenium 点击链路，前端按钮与 API 的联动靠既有页面与人工抽查。
4. **备份恢复演练**：基线 §六 要求「上线前完成一次恢复演练并记录实测 RTO」，本方案未覆盖，是明确的遗留项。
5. **加密与传输**：bcrypt 口令、HTTPS、内网可达性属于部署验收，不在应用层用例里。
6. **LLM 真实上游**：故障场景验证的是错误码契约与回落路径，没有真实调用外部模型服务。

## 九、如果失败，怎么处置

| 现象 | 先查 | 常见原因 |
|---|---|---|
| N06 成功 > 1 单 | `UNIQUE(device_id, slot_date, slot_start, active_flag)` 是否还在 | 迁移脚本漏建索引 |
| B01 日期边界错 | `slots.BOOKING_WINDOW_DAYS` 与 `check_date` 的 `>` / `>=` | 差一天错误 |
| B04 时间容差错 | `_normalize_returned_at` 的 5 分钟与本地时区 | 机器时区与 CI 的 UTC 不一致 |
| P06 未锁定 | `MAX_FAILED_ATTEMPTS` / `LOCK_MINUTES` 与 `record_login_failure` | 计数被成功登录清零 |
| F03 旧索引丢失 | `rag.rebuild` 是否先构建到临时对象再替换 | 原地清空后构建 |
